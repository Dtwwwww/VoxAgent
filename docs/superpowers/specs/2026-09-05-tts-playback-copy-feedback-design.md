# 朗读可靠性、低延迟音色与复制反馈设计

## 1. 目标

在保持声灵完全本地运行、文字输入不自动发声、LLM 继续优先使用 GTX 1660 Ti 6GB 显存的前提下，解决以下三个已复现的体验问题：

1. 点击“朗读”后可能没有声音，也没有及时显示发声状态。
2. 当前音色生硬、等待时间长，不像自然对话。
3. 点击“复制”后没有成功或失败反馈。

本次采用“响应速度优先”的方案：使用已经安装并完成本机基准测试的 MeloTTS 作为默认引擎，不下载大型语音模型，不让 TTS 与 4B LLM 竞争 GPU。

## 2. 现状与根因

### 2.1 朗读无声

前端点击“朗读”时，只清理旧队列并发送 `assistant.speak`。`AudioPlayback` 在服务端返回 WAV 后才创建 `AudioContext`，而且从未调用 `resume()`。浏览器可能把这个脱离原始点击手势创建的音频上下文保持在 `suspended` 状态，因此消息和 WAV 都正常，用户仍听不到声音。

前端也只在第一段 WAV 解码并排入播放队列后，才把 `speakingTurnId` 和全局 `voiceStatus` 改成正在朗读。服务端合成期间没有任何可见状态。当前 Kokoro 在目标电脑上的首次音频延迟 p50 为 11.3–12.3 秒，用户会在这段时间内看到按钮毫无变化。

### 2.2 声音不自然且慢

当前唯一公开音色是 Kokoro `native_voice_id=3`。目标电脑基准显示，它的首次音频延迟 p50 为 11.3–12.3 秒、p95 为 12.7–14.3 秒。已安装的 MeloTTS 首次音频延迟 p50 为 1.5–2.0 秒、p95 为 1.7–2.3 秒，峰值进程内存约 397MB，与 Kokoro 约 413MB 接近。

用户先前盲听并列选择的 `engine-002`、`engine-003`、`engine-004` 中，一个来自 Kokoro、两个来自 Melo，因此切换到 Melo 不违背已有主观评审结果。当前浏览器播放链路还额外施加了 `1.15` 倍增益，峰值较高的 PCM 可能在输出端削波，进一步损害清晰度。

手动朗读目前会把整条回复一次性交给 TTS；文本越长，首次发声越晚。朗读预处理仅删除 emoji，Markdown 标记、网址、代码片段、列表符号和异常换行仍可能被引擎生硬读出。

### 2.3 复制无反馈

消息组件只执行 `navigator.clipboard?.writeText(message.text)`，没有保存请求状态、没有捕获失败，也没有在 Clipboard API 不可用时执行兼容回退。可选链还会让“不支持剪贴板 API”静默成为一次无操作。

## 3. 方案选择

采用方案 2：MeloTTS 默认音色 + 完整朗读状态机 + 浏览器音频解锁 + 复制反馈。

未采用的方案：

- 只修 UI、保留 Kokoro：风险最低，但 11–14 秒等待和音色问题不解决。
- 根据文本动态切换两个引擎：会让同一个 Agent 的声音不一致，同时增加取消、队列和测试复杂度。
- 引入 CosyVoice、GPT-SoVITS 等大型模型：可能获得更高自然度，但不符合本次“响应速度优先”和“不争抢 6GB GPU”的约束。

## 4. 产品交互设计

### 4.1 单条消息朗读状态

每条可朗读的 Agent 消息拥有独立状态：

| 状态 | 按钮文案 | 图标与表现 | 可执行操作 |
| --- | --- | --- | --- |
| `idle` | 朗读 | 扬声器 | 开始朗读 |
| `preparing` | 准备中 | 小型旋转指示器 | 可点击停止 |
| `playing` | 正在朗读 | 三条动态声波 | 可点击停止 |
| `error` | 重试朗读 | 警示图标，短暂红色 | 重新开始 |

用户点击后必须在 100ms 内进入 `preparing`，不等待服务端返回。任一时刻最多只有一条消息处于 `preparing` 或 `playing`；朗读另一条消息会停止前一条。

底部现有状态栏同步显示：

- `preparing`：`正在生成朗读…`
- `playing`：`正在朗读`
- 播放完成或停止：隐藏朗读状态，恢复空闲
- 失败：现有错误提示区显示具体错误，消息按钮进入 `error`

移动端保留 44×44px 可点击区域；即使隐藏按钮文字，也通过 `aria-label` 暴露“准备朗读”“停止朗读”“重试朗读”。状态变化使用非打断式 `aria-live="polite"`。

### 4.2 复制反馈

复制状态保存在单条消息组件内，互不影响：

- 点击后成功：复制图标变为绿色勾选，文字显示“已复制”。
- 1500ms 后恢复“复制”。
- 失败：图标和文字显示“复制失败”，同时保留按钮以便重试；2500ms 后恢复。
- 连续点击会取消旧计时器并重新计时；组件卸载时清理计时器。
- 桌面端和移动端都使用 `aria-live="polite"` 通知状态。

优先使用 `navigator.clipboard.writeText`。在 API 不存在时，使用临时只读 `textarea`、选区保存/恢复和 `document.execCommand("copy")` 进行本地回退；两条路径都失败时必须显示失败，不能静默处理。

## 5. 朗读数据流与状态机

### 5.1 用户点击阶段

1. `ChatMessage` 调用 `speakMessage(turnId)`。
2. `useVoiceSession` 立即把该轮次设置为 `preparing`，清理上一次朗读。
3. 在这次真实点击手势内调用 `AudioPlayback.unlock()`：创建或复用 `AudioContext`，若状态不是 `running` 则执行 `resume()`。
4. 解锁成功后发送 `assistant.speak`；WebSocket 未连接或解锁失败时进入 `error`，不发送无意义请求。

`unlock()` 是公开的异步方法，但对 `resume()` 的调用必须同步发生在点击调用栈内，后续只等待其 Promise 结果。

### 5.2 服务端阶段

服务端验证轮次属于当前会话且助手消息已经完成后，先发送：

```json
{"type":"tts.started","session_id":"…","turn_id":7}
```

该事件表示请求已接受并开始合成，不表示已经有声音。然后服务端对清洗后的文本按完整句子分段，依次合成并发送现有的 `tts.chunk` + WAV 二进制数据。首句完成后立即发送，不等待整条消息。

每段必须保持连续递增的 `sequence`。最后一段已经发送后，服务端发送：

```json
{"type":"tts.done","session_id":"…","turn_id":7}
```

`tts.done` 表示不会再收到新的分段，但不代表浏览器已经播放完毕。取消时沿用 `turn.cancel` / `turn.cancelled`；失败沿用 `error`，并确保当前轮次从活动状态退出。

### 5.3 浏览器播放阶段

1. 收到 `tts.started` 后维持 `preparing`，用于确认服务端已接受。
2. 第一段 WAV 成功解码并调用 `source.start()` 后进入 `playing`。
3. 后续分段按 `sequence` 排队，使用已有 `tailTime` 无缝衔接。
4. 收到 `tts.done` 后把本地队列标记为完整；只有队列、解码任务和音源全部结束才回到 `idle`。
5. 用户停止、发起新对话、开始麦克风输入、断线或清空数据时，必须同时清理本地音源、待解码数据和消息状态。

如果 `AudioContext` 又被浏览器挂起，播放前再执行一次 `resume()`；恢复失败抛出可识别的 `audio_context_blocked` 错误，不把“已排队”误报为“正在朗读”。

## 6. 轻量音质优化

### 6.1 默认引擎

- 保留公开键 `default_voice`，将它映射到 MeloTTS `native_voice_id=0`，确保现有浏览器设置无需迁移。
- 展示名称改为“声灵快速音色”，描述为“响应更快，适合日常对话”。
- 将原 Kokoro 音色作为非默认公开键 `original_voice` 保留，展示名称为“声灵原声音色”，便于用户比较和一键回退。
- 默认语速保持 `1.0×`；继续支持 `0.8×`、`1.0×`、`1.2×`。
- 两个引擎均继续使用 CPU；不得把 TTS 切换到 CUDA。

### 6.2 文本清洗与分段

新增独立、可单元测试的朗读文本规范化模块，仅影响送入 TTS 的副本，不修改屏幕文本或持久化消息：

- 删除 emoji 及变体选择符。
- Markdown 链接保留可读标题、删除 URL；裸 URL 替换为“链接”。
- 删除围栏代码块；行内代码保留文本内容，不朗读反引号。
- 标题、引用、项目符号转换为自然停顿。
- 连续空白折叠；中英文标点统一为引擎容易停顿的形式。
- 空清洗结果不启动 TTS，并返回可恢复错误。
- 以 `。！？；` 及合理逗号边界切分，单段最长 120 个 Unicode 字符；不能在英文单词、数字或 Markdown 转换后的短语中间硬切。

### 6.3 播放输出

- 浏览器 `GainNode` 从 `1.15` 调整为 `1.0`，避免额外削波。
- 不加入混响、变调、降噪或动态压缩，避免增加延迟和引入新的失真。
- 音量继续由系统和浏览器控制。

上述措施改善清晰度、停顿和首声速度，但不会把轻量 MeloTTS 变成大型生成式真人音色。更高自然度模型属于后续独立项目。

## 7. 组件边界

- `frontend/src/audio/playback.ts`：只负责音频上下文解锁、解码、排队、播放、停止和完成通知。
- `frontend/src/useVoiceSession.ts`：拥有当前朗读轮次及阶段，处理协议事件和错误映射。
- `frontend/src/components/ChatMessage.tsx`：渲染消息动作状态；复制反馈为本地 UI 状态，不进入会话控制器。
- `frontend/src/components/VoiceStatus.tsx`：把朗读阶段映射为底部状态栏文案和动画。
- `backend/src/voxagent/speech/text_normalization.py`：纯函数完成朗读清洗与分段。
- `backend/src/voxagent/conversation/events.py`：定义严格的 `TtsStarted` 与 `TtsDone` 服务端事件。
- `backend/src/voxagent/conversation/orchestrator.py`：验证朗读请求、发送开始事件、逐段合成、处理取消和终止。
- `backend/src/voxagent/speech/voice_catalog.json`：只保存公开音色与内部引擎映射。

协议夹具必须同步更新，后端与前端都严格拒绝字段缺失、额外字段和错误类型。

## 8. 错误处理

| 场景 | 用户反馈 | 状态恢复 |
| --- | --- | --- |
| WebSocket 未连接 | “本地语音服务未连接” | 当前消息 `error` |
| 浏览器音频无法解锁 | “浏览器未允许播放声音，请再次点击朗读” | 当前消息 `error` |
| 轮次不可朗读 | “这条消息暂时不能朗读” | 当前消息 `error` |
| TTS 合成失败 | “朗读生成失败，请重试” | 清队列并进入 `error` |
| WAV 无效或解码失败 | “音频播放失败，请重试” | 清队列并进入 `error` |
| 复制权限/API 失败 | 按钮显示“复制失败” | 2.5 秒后恢复 |

错误不能关闭 WebSocket，文字对话仍可继续。错误消息不得包含本地模型路径、原始异常或内部音色编号。

## 9. 测试与验收

### 9.1 自动化测试

前端必须覆盖：

- 点击后立即进入 `preparing`，并在发送 WebSocket 消息前调用音频解锁。
- `AudioContext` 为 `suspended` 时调用 `resume()`；失败时不发送朗读请求。
- `tts.started → tts.chunk → tts.done → 播放完成` 的完整状态转换。
- 停止、切换消息、麦克风打断、断线、迟到 WAV 和解码竞态。
- 复制主路径、API 缺失回退、失败提示、计时恢复和卸载清理。
- 移动端按钮仍有正确 `aria-label`，底部状态栏文案正确。

后端必须覆盖：

- 只有可朗读轮次才发送 `tts.started`，每条已开始的正常朗读恰好发送一个 `tts.done`。
- 多句文本按顺序产生多个 `tts.chunk`，首段无需等待后续段。
- Markdown、emoji、网址、代码和长文本的确定性清洗与分段。
- 取消后不发送迟到音频，终止批次只出现一次。
- `default_voice` 路由到 Melo，`original_voice` 路由到 Kokoro，公开响应不泄露引擎和原生音色 ID。

### 9.2 目标电脑验收

- 点击“朗读”后 100ms 内出现“准备中”。
- 常用 10–25 字中文句子首次可听声音目标不超过 3 秒；以现有 Melo p95 2.3 秒基准为依据。
- 连续朗读同一条消息 3 次都能出声；停止后 300ms 内静音。
- 朗读过程中按钮和底部状态栏均显示状态，完成后自动恢复。
- Markdown、emoji、网址和代码符号不被生硬朗读。
- 默认播放无明显削波爆音；系统音量正常时语音清楚可辨。
- 复制中文、英文、多行文本均显示“已复制”，粘贴内容与原消息完全一致。
- 文字输入仍只产生文字回复；语音输入仍产生文字和语音回复。

验收必须在实际浏览器和目标电脑执行，不能只依赖模拟的 Web Audio 测试。

## 10. 非目标

- 不下载或接入云端 TTS。
- 不做声音克隆。
- 不训练或微调音色。
- 不让 Melo/Kokoro 使用 GPU。
- 不改变 ASR、VAD、LLM、RAG、记忆和知识库行为。
- 不恢复“文字消息自动朗读”。
- 不承诺轻量 TTS 达到真人录音级自然度。

## 11. 交付顺序

1. 先修浏览器音频解锁和逐消息朗读状态，解决“无声、无反馈”。
2. 再实现复制成功/失败反馈，形成独立可验收增量。
3. 增加 `tts.started` 协议和服务端分段合成。
4. 切换 Melo 默认音色、保留 Kokoro 回退，并移除额外增益。
5. 完成自动化回归与目标电脑浏览器验收，更新 Plan 2 使用手册和基准记录。
