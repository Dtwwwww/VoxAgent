# 本地实时语音与连续播放优化设计

## 目标

实时通话默认使用本地语音链路（SenseVoice + Ollama + Kokoro），并在保持较低首句延迟的前提下，减少流式语音因片段过短造成的断裂、停顿和音色跳变。

## 已确认的现状

- 当前前端默认语音模式为 `online-preferred`，在线路径依赖浏览器 Web Speech API，识别结果不稳定。
- 本地路径可以完成 VAD、ASR、Ollama 回复和 Kokoro 合成。
- 模型回复通过 `assistant.delta` 流式到达，前端由 `StreamingSentenceQueue` 切分后逐段调用浏览器语音或本地回放。
- 文字输入保持静默，不触发自动语音。

## 方案决策（方案 C）

### 1. 本地模式优先

- 新用户默认 `local-only`。
- 已保存为 `online-preferred` 的设置在首次读取时迁移为 `local-only`，用户仍可在界面手动切回在线模式。
- 本地模式继续把 PCM 帧发送到后端，由服务端完成 VAD/ASR；WebSocket、会话、RAG、记忆和 Ollama 流程不变。

### 2. 流式片段合并

在 `StreamingSentenceQueue` 与回放泵之间增加轻量合并规则：

- 句号、问号、感叹号、分号等强边界立即输出。
- 逗号、顿号、冒号等弱边界只有在累计长度达到最小阈值（建议 12 个 Unicode code point）时才输出。
- 过短片段会与下一个片段合并；累计达到最大阈值（建议 28 个 Unicode code point）时强制输出，避免等待过久。
- 回答结束时刷新剩余缓冲，保证尾句不会丢失。
- 取消、打断、切换模式和 WebSocket 断开时清空缓冲，禁止旧片段串入新回合。

该策略不改变对话文本、历史记录或服务端协议，只改变前端播放分段；首句仍可在流式生成期间开始播放。

## 交互与状态

- 实时通话按钮、麦克风音量条和底部状态栏保持现有行为。
- 本地 ASR 的临时字幕继续实时显示；最终识别结果才写入永久用户消息。
- 播放期间仍可打断；打断后立即清空待播片段并回到监听状态。
- 本地 TTS 失败时沿用现有可恢复错误提示，不影响文字回复。

## 验收标准

1. 新安装或迁移后的实时通话显示“仅本地”，无需在线语音确认即可开始。
2. 连续短 `assistant.delta`（如 2–5 字）不会逐段播放，而会合并成更长自然片段。
3. 强标点仍能及时触发播放；单段不会超过最大阈值太久。
4. `assistant.done` 后所有尾部文本都能播放；取消后不会播放残留文本。
5. 现有本地语音、文字静默、复制、朗读/停止和 WebSocket 回归测试保持通过。

## 不在本次范围

- 更换 Kokoro 模型或引入新的 TTS 引擎。
- 修改在线 Web Speech API 的识别算法。
- 改造服务端 LLM、RAG 或记忆逻辑。
- 追求完全真人音色；本次只优化片段连续性和播放节奏。
